1. Two Types of Devices: Android vs. Apple iOS

Android Ecosystem Open Mindset

Philosophy & Foundation: Open mindset, originating as AOSP (Android Open Source Project) written by Google. Adapted and modified by OEMs and SoC chipmakers (Qualcomm, MediaTek) with custom kernels, drivers, and UI skins.

Runtime Execution: Apps run through the Android Runtime (ART) as Dalvik Executable (.dex) bytecode, utilizing profile-guided AOT and JIT compilation.

Sideloading: Natively permits sideloading (users enable unknown sources per-app).

Boot Chain: BootROM → Secondary Bootloader (XBL/ABL) → fastboot & Android Verified Boot (AVB). Bootloader unlocking is officially supported by many OEMs via fastboot flashing unlock, wiping userdata.

Composed Of:

  • Linux Kernel: Custom LTS kernel, unified under GKI (Generic Kernel Image) since Android 12, with vendor modules.
  • System Libraries & Daemons: init, ueventd, servicemanager interfacing with /dev, /sys, /proc; Bionic libc and BoringSSL.
  • HAL: Standardized AIDL/HIDL interfaces decoupling framework from hardware drivers.
  • ART: Executes .dex bytecode.
  • System Services & Framework: Coordinated by system_server, exposing android.* APIs.
  • Android API: Public SDK defining available platform functionality per API level.
Apple iOS Ecosystem Proprietary / Closed

Philosophy & Foundation: Closed-source, proprietary ecosystem. Vertically integrated: Apple designs silicon (A/M-series SoCs), Secure Enclave, firmware, OS, and hardware.

Platform Lockdown: Officially locked down. The EU Digital Markets Act (DMA) introduces limited EU-only alternative marketplaces and notarized sideloading.

Boot Chain: SecureROM (hardware ROM) → LLB / iBoot → XNU Kernel. Locked down by hardware efuses, Apple Root CA, and personalized cryptographic validation against Apple TSS signing servers (SHSH blobs). Legitimate bootloader unlocking is impossible.

Sealed Filesystem: Signed System Volume (SSV) with APFS snapshots prevents modifications to the root filesystem.

Composed Of:

  • Cocoa Touch: Key frameworks (UIKit, SwiftUI) for UI presentation, touch event loops, and app lifecycle.
  • Media Layer: Hardware-accelerated graphics (Metal, Core Animation) and audio/video pipelines (AVFoundation).
  • Core Services: Foundational non-UI services including Foundation, Core Data, CloudKit, and Network.framework.
  • Core OS Layer: Low-level hardware interfacing, Security.framework, libSystem (POSIX), and local hardware authentication.
  • Darwin (XNU Kernel): Hybrid kernel combining Mach (IPC, virtual memory, threads) and BSD (networking, VFS, POSIX permissions, MAC/Seatbelt sandbox).
  • Hardware & Secure Enclave: Apple Silicon hardware root of trust, Secure Enclave Processor (SEP), and hardware AES cryptographic engines.

4. Privilege Escalation & Jailbreaking Evolution

Android Root Evolution

Pre-4.4: Direct userspace & DAC bugs (e.g., rageagainstthecage, zergRush taking over root-owned daemons like adbd or vold).

4.4 – 9: SELinux enforcement (introduced in 4.4 permissive, 5.0 enforcing) closed userspace DAC attacks, forcing privilege escalation into the Linux kernel (e.g., towelroot CVE-2014-3153). Root solutions transitioned from modifying /system (SuperSU) to systemless boot partition patching (Magisk hooking init and dynamically modifying SELinux policy rules).

10+: Generic Kernel Image (GKI) standardized the kernel across OEMs. Enabled kernel-level root solutions: KernelSU (integrated into GKI kernel source) and APatch (patching kernel via KernelPatch without userspace ramdisk modification).

Apple iOS Jailbreak Evolution

Pre-9: 1-click web/browser jailbreaks (e.g., JailbreakMe) utilizing WebKit memory corruption bugs chained with kernel vulnerabilities to execute unsigned code.

10 – 14: Kernel heap corruption/UAF exploits providing tfp0 (task_for_pid 0) enabling semi-tethered jailbreaks (unc0ver, Taurine). Unpatchable BootROM vulnerability (checkm8 on A5–A11 chips) enabled tethered jailbreaks (checkra1n, palera1n) regardless of iOS version.

15+: Hardware mitigation layers introduced: PAC, PPL, and SPTM/TXM. Modern exploitation relies on rootless jailbreaks (leaving SSV root filesystem untouched, staging in /var/jb like Dopamine) and signature verification bypasses (e.g., CoreTrust bugs enabling TrollStore).

5. Root & Elevated Access Without Magisk/SuperSU

1. Modern Kernel-Level Solutions (Unlocked Bootloader)
  • KernelSU: Integrated directly into the GKI Linux kernel; grants root via kernel syscall interception (prctl/su) without touching userspace init.
  • APatch: Injects hooks into the boot image kernel using KernelPatch without modifying initramfs or triggering Magisk-specific detection.
2. OEM-Authorized / Built-in Methods (No Root Tools)
  • AOSP Userdebug / Engineering Builds: Building AOSP target with userdebug or eng gives native root access via adb root out of the box with su included.
  • Official Emulators (Android Studio AVD): Use system images labeled "Google APIs" (instead of "Google Play") which natively support running adb root directly.
3. Testing Without Unlocking Bootloader / Keeping OEM Locked (Bypassing Root Requirement)
  • Frida Gadget Repackaging: Inject libfrida-gadget.so into the target APK using objection patchapk or apktool. Allows full dynamic instrumentation, SSL pinning bypass, and memory inspection on a 100% stock, locked device without requiring root.
  • Shizuku / Wireless ADB: Grants elevated uid 2000 (shell) privileges via ADB/WiFi debugging APIs to interact with app components and data without needing full uid 0 root.
  • LPE 1-day / 0-day exploits: Gaining transient in-memory root privileges via an unpatched kernel vulnerability without persistently modifying firmware partitions.

Android 13 33 Granular media permissions (READ_MEDIA_IMAGES, etc.). Legacy READ_EXTERNAL_STORAGE is inert; test granular access controls.

Custom Scheme Deep Links

Defined via custom URI schemes (e.g., myapp://gizmos):

<intent-filter>
    <action android:name="android.intent.action.VIEW" />
    <category android:name="android.intent.category.DEFAULT" />
    <category android:name="android.intent.category.BROWSABLE" />
    <data android:scheme="myapp" android:host="gizmos" />
</intent-filter>
  • No Verification: Any application can register the same custom scheme; susceptible to interception.
  • Android 12+ Behavior: Web intents open in browser by default unless verified; custom schemes remain unverifiable.
Android App Links (autoVerify="true")

Cryptographically verifies domain association via Digital Asset Links:

<intent-filter android:autoVerify="true">
    <action android:name="android.intent.action.VIEW" />
    <category android:name="android.intent.category.DEFAULT" />
    <category android:name="android.intent.category.BROWSABLE" />
    <data android:scheme="https" android:host="example.com" />
</intent-filter>
  • Hosted at https://example.com/.well-known/assetlinks.json with SHA-256 cert fingerprint.
  • Eliminates the disambiguation dialog and opens content directly.
What autoVerify Does NOT Prevent Verification proves who receives the URL, not who sends it or what payload it carries. Verified App Links remain completely vulnerable to parameter tampering, directory traversal, cross-app scripting, and internal open redirects into WebViews (loadUrl()).
OWASP MASTG Standards & Testing CLI

Standards: MASTG-TEST-0393 (Unverified App Links) and MASTG-TEST-0394 (Missing Input Validation in Scheme Handlers).

8. Obfuscation, Commercial RASP & Native Packers

R8 / ProGuard (Free / Built-in)

Name Mangling Only: R8 only renames classes, methods, and fields for DEX size reduction (com.example.MyActivity → a.b.a).

Zero Advanced Protections: R8 provides no control-flow flattening, no string encryption, no class encryption, no call hiding, no code virtualization, and no runtime self-protection (RASP).

Reversibility: A leaked mapping.txt fully collapses all R8 obfuscation via the retrace CLI tool.

Commercial App Hardening & Shielding

Advanced Code Hardening: Applies control-flow flattening, opaque predicates, string/asset encryption, and code virtualization (transforming methods into proprietary VM bytecode).

Runtime Application Self-Protection (RASP): Actively detects root/jailbreak, debuggers, emulators, hook frameworks (Frida, Substrate), and repackaging.

Flutter Internal Architecture

Debug Mode: Uses Dart VM with Just-in-Time (JIT) compilation and hot-reload; package contains kernel_blob.bin.

Release Mode: Compiles Ahead-of-Time (AOT) into native shared libraries:

  • Android: libapp.so (app logic) + libflutter.so (engine).
  • iOS: App.framework/App + Flutter.framework/Flutter.

Snapshot Hash: libapp.so is coupled to the exact engine snapshot version; tooling must match this hash.

The Proxy & CA Trust Store Myth

Proxy Blindness: dart:io's HttpClient completely ignores Android system proxy settings. Traffic flows direct unless findProxy is configured in Dart code.

Trust Store Reality: Dart on Android does not compile in root certs. Dart SDK source (security_context_linux.cc) proves it directly reads /system/etc/security/cacerts.

The Root Cause: Burp CAs installed via Android settings land in the user store, which Dart never reads. Pushing CA to the system store works natively!

10. Consolidated Pentesting Checklist & Retesting Workflow

Execution Phase 1: Static Discovery & Reconnaissance
  • Identify architecture: Check if app is native Java/Kotlin, Flutter (libflutter.so), or React Native.
  • Decompile APK/IPA using JADX / apktool / Ghidra; inspect manifest for android:debuggable="true".
  • Review all <intent-filter> elements: Flag HTTP/S filters missing android:autoVerify="true" (MASTG-TEST-0393).
  • Identify all exported activities, services, and content providers lacking permission barriers.
Execution Phase 2: Traffic Interception Setup
  • Android API 24+: Push Burp CA to /system/etc/security/cacerts/ (rooted) or patch Network Security Config via apktool.
  • iOS: Install CA profile AND enable Full Trust under Settings → General → About → Certificate Trust Settings.
  • Flutter apps: Use ProxyDroid / iptables DNAT or patch via reFlutter / NVISO Frida script.
Execution Phase 3: Runtime Fuzzing & IPC Exploitation
  • Query App Link verification state on device using adb shell pm get-app-links --user cur <pkg>.
  • Fuzz deep link intent handlers for parameter tampering, auth bypass, and open redirects into WebViews (MASTG-TEST-0394).
  • Dynamic Code Loading: On Android 14+ targets, audit whether dynamically loaded DEX files are marked read-only before execution.
  • Evaluate RASP & Anti-Tampering: Check if Appdome Build-to-Test flag is active, or trace memory checks using Frida.
